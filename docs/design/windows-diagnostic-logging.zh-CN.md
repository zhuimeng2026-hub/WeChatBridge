# Windows 诊断日志实现复核与改进

- 日期：2026-10-26。
- 复核基线：远程 `codex/desktop-archive-design` 的 `82aeaa5`，包含精简桌面端、WorkBuddy 接收服务、打开知识库修复及诊断日志增强。
- 范围：本地诊断日志写入、轮转、异常上下文及诊断包导出；不新增业务页面、出口或云端日志服务。
- 具体实现使用 `gpt-6-luna`，主代理复核代码、验证并提交。

## 1. 保留现有轻量方案

远程已提供 `DiagnosticLog`、`DiagnosticSink`、环境快照、全局异常记录，以及设置中的“导出诊断日志 / 打开日志目录”。该职责划分适合当前小型桌面工具，可以沿用，不需要为了几类文件日志引入新的日志框架和依赖。

诊断日志只用于解释运行过程，不代替 `ReceptionService` 的任务、收据及恢复状态。日志轮转或导出失败不能改变某条聊天记录的归档结果。

本轮改进聚焦已核实的缺陷，而不是增加更多采集点：

| 问题 | 实际后果 | 改进 |
| --- | --- | --- |
| `static lock` 只在单个进程内有效，主程序与 ShareTarget 共写同一文件 | 并发打开和轮转失败后异常被吞，诊断事件丢失 | 按日志路径建立跨进程互斥，写入、轮转和快照共用 |
| 异常只记录最外层类型、Message 和 StackTrace | 内层 I/O、聚合 Task 异常原因缺失 | 保留完整异常链，并压成单事件单行 |
| 单条消息没有大小上限，轮转只检查写前长度 | 超长消息可突破文件容量；轮转失败仍可能增长 | 按 UTF-8 字节限制事件，按待写字节预测轮转 |
| 导出匹配 `windows.log*` | 意外包含任意同前缀文件 | 只允许当前日志和三代轮转文件 |
| 先创建 ZIP 条目再打开源日志，读取失败被吞 | 导出包可能有空日志且没有遗漏说明 | 先取得快照，再创建内容条目，遗漏单独说明 |
| 用秒级时间戳命名且直接写最终 ZIP | 连续导出冲突，失败后可能留下半包 | 唯一文件名；只清理本次创建的未完成包 |

## 2. 原版缺陷复现

从 `82aeaa5` 提取原始 `DiagnosticLog.cs`，在隔离的 .NET 10 控制台中调用同一实现；`InboxPaths` 替身仅提供日志目录。使用 6 个独立子进程，每个在共同启动信号后写入 1,500 条带进程编号和序号的事件。

该次运行应写入 9,000 条，实际保留 4,093 条，缺失 4,907 条。日志总量小于轮转阈值，因此丢失不能用正常淘汰旧日志解释。具体缺失数量受进程调度影响，不作为固定断言；回归必须断言本次负载下每个事件完整、唯一。

替换为修复后的实现，使用同一个隔离控制台及相同 6 × 1,500 负载再次运行：保留 9,000 条，唯一事件 9,000 条，本次缺失为 0。仓库中的另一个子进程回归使用 6 × 1,200 条、每条附加 512 字节负载，额外验证真实轮转后所有事件仍在保留范围内。

仅使用多线程测试不能证明此缺陷被修复；跨进程互斥需要真实子进程回归。

## 3. 写入与容量契约

- 文件名沿用 `windows.log`；保留 `INFO / WARN / ERROR`、UTC 时间戳及 UTF-8 无 BOM，新增进程 ID 以区分主程序和分享助手。
- 同一规范化路径生成同一互斥名；Windows 下忽略路径大小写，避免不同调用方实际写同一文件却拿到不同锁。
- Windows 使用本地会话命名空间，其他系统使用对应可用的命名方式。独立用户会话、不同路径别名及不遵守协议的外部写入者不属于该锁的协调保证。
- 等待互斥有上限；拥有锁的进程异常退出后，后继进程接受 abandoned mutex 并继续处理。
- 单事件包括末尾换行最多 64 KiB，按 UTF-8 字节截断，保留截断标记；不能切坏多字节字符。
- 当前日志最多 4 MiB，最多保留 `.1`、`.2`、`.3` 三代，`.1` 最新。新写入按“现有大小 + 本条字节数”判断是否轮转。
- 轮转失败且即将越界时跳过该事件，不继续增长、不截断旧文件。磁盘损坏、权限、锁超时等场景仍属于 best-effort，不能承诺所有机器上绝不丢日志。
- 写入只创建日志目录，不为每条事件创建整套 Inbox 子目录。
- `InboxLogger` 旧签名及 `DiagnosticSink` 保持兼容，调用方无需整体迁移；日志异常不得抛回业务流程。

旧版已产生的大文件可能仍超过新版上限。导出读取这些文件时必须有独立容量边界，不能假定新写入规则会追溯约束所有历史日志。

## 4. 诊断包导出契约

导出先在与写入、轮转相同的互斥下获取文件快照，再释放互斥进行 ZIP 压缩。快照之后的新事件留待下一次导出；不为整个压缩过程锁住日志写入。

只考虑四个确切文件名：`windows.log`、`windows.log.1`、`windows.log.2`、`windows.log.3`。不枚举通配前缀，不包含诊断包自身、收据、任务文件、聊天 ZIP、知识库笔记、账号或授权配置文件。

每个日志快照最多保留 4 MiB；读取旧版超限文件时保留尾部并在说明中标出截断。来源缺失、不可读、锁等待超时也分别列明，不以空日志条目伪装成正常导出。日志全部缺失时仍可生成说明包，明确当前没有可用日志。

输出文件名具备唯一性，使用排他创建，不覆盖已有包。只有本次创建且尚未完成的文件允许在失败时清理，用户先前的导出保持原样。

摘要和界面文案应如实说明：导出不主动收集聊天原文、笔记正文和账号配置文件，但已有运行日志可能包含文件路径、Windows 用户名、聊天或笔记文件名以及异常消息上下文。不能用“包含每一步与全部错误”或“保证无任何用户信息”概括 best-effort 日志；分享前用户可检查内容。

## 5. 验证要求与边界

| 验证 | 必须证明 |
| --- | --- |
| 原接口及级别 | 旧调用继续工作，时间、级别和中文可读 |
| 异常链 | InnerException、AggregateException 的具体原因和调用栈保留，事件仍为单行 |
| 大消息及轮转 | UTF-8 上限成立、超长事件可辨识、保留代数和顺序正确 |
| 真实多进程写入 | 多个子进程并发时，本次未超出总保留量的事件完整且唯一 |
| 写入期间导出 | 快照有效、ZIP 可读，导出不使本次写入事件丢失 |
| 白名单与遗漏 | 同前缀额外文件不会入包；缺失、不可读有明确说明，无伪造空条目 |
| 重复导出 | 连续操作得到不同完整文件，既有包不被覆盖 |
| 故障不干扰业务 | 不可写路径或锁问题不会让日志异常逃逸到调用方 |

测试仅使用临时日志和探针进程，不使用真实微信聊天或改写用户的 Obsidian 配置。真实微信转发及 Obsidian 界面打开的全流程不属于本轮日志修复的完成声明。
