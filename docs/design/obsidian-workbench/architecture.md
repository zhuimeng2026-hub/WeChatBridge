# 共用架构与实施顺序

## 数据与状态

沿用现有 `ObsidianSettingsStore` 的 `vaultPath` / `subfolder`。Core 服务只处理用户选择的本地库，不读取微信数据库，不自动上传聊天。工作台维护一个当前状态，布局切换仅重排视图。

输入分为原文、文件路径、附件和明确选中的材料。Markdown 是可读文本；PDF、图片、音视频、ZIP 作为附件定位或交给外部模型，不把二进制当作已提取正文。OCR、PDF 解析和全库向量索引不在本次内。

## 文件边界

以规范化库目录为根，拒绝绝对路径、目录穿越与越界链接；隐藏配置目录与不支持文件不纳入正文检索。读取需限制文件大小并处理读写异常。保存仅允许新 `.md` 文件，拒绝重名覆盖，保留 Markdown 来源路径和时间。

## LLM 工作流

使用现有转发目标或明确复制请求，用户检查本次材料后交给已安装 AI Agent；答案返回工作台草稿供核对和另存。示例数据与本地演示结果有持续标签。尚未接入供应商 API、流式响应或自动回传，因此 UI 不显示虚假生成成功。

后续若直连模型，必须放在订阅形态的网络边界中，按库/案件划分作用域，并清晰列出上传材料。不要给买断版增加网络类型引用。

## 阶段

1. WB-0：保存三份原稿、方案说明、共用技术设计、客户演示与验证状态。
2. WB-3：Core 文件服务 + 共享状态 + 阅读优先布局 + 主程序入口；为目录边界与创建笔记添加有意义的测试。
3. WB-2：基于共用状态增加案件列表、材料选择条与双栏工作区。
4. WB-1：增加文件树/原文/助手三栏工作台；保持三种布局随时可切换。
5. WB-QA：Windows 双形态 CI、现有测试/无网络门禁、原生截图与对照原图。每个阶段独立提交。

## CI 与发布

构建、安装依赖、执行测试全部由 GitHub Actions。当前环境只编辑与静态复核，不在本机运行构建/测试。公开仓库推送需授权，尚未获准前不能声称云端 CI 通过或已发布给客户。

## 本次适配的现有数据格式

`ObsidianNote.Render` 生成的 `[[附件/原始归档.zip]]` 与 `![[附件/图片.png]]` 会按笔记目录解析并在库边界内定位。相邻附件也会列出；不会读取或发送二进制内容。其他非本地/越界引用不会自动访问。

请求导出成功后保留提示词、工具、来源路径与选段快照；同一库刷新保留这些记录。不同库的结果不得直接保存为新库的分析笔记，需明确开始新分析。
