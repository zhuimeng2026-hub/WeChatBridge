# Windows 精简桌面端详细设计

- 日期：2026-10-26
- 状态：待实现的设计规格；本次只编写文档，不代表界面或服务已经改造。
- 适用范围：Windows WPF 桌面端，微信聊天通过 WorkBuddy 导出后归档到 Obsidian。
- 配套设计：[WorkBuddy 自动检测与可靠归档](windows-workbuddy-auto-detection.zh-CN.md)。
- 源码核对：本地需求讨论基线 `0a3133e`，提交前已对照远程 `main` 的 `4190f38`；保留主线已有品牌与附件分类能力。

## 1. 产品目标与边界

用户在微信里选择聊天记录并转发到 WorkBuddy，桌面端自动接收其导出的本地 ZIP，转换为 Markdown 和附件，保存到用户指定的 Obsidian 知识库。

桌面端只让用户确认三件事：当前是否在接收、记录保存在哪里、最近一次是否保存成功。WorkBuddy 是来源，Obsidian 是唯一出口。

本轮设计不新增聊天浏览器、AI 对话、总结、搜索知识库、任务编排、统计看板或其他出口。归档不要求 Obsidian 进程正在运行，也不要求配置 WorkBuddy 账号、接口地址、端口或密钥。

本设计收敛 Windows 产品面，不修改 macOS 的多出口产品，也不在本轮设计中改变已有登录、授权、更新和服务端协议。已有授权门禁若适用于当前发行形态，继续沿用；授权信息只放设置底部，不增加主窗口导航。

## 2. 当前实现与改造范围

现有主窗口是设置型侧边栏，包含通用、场景、技能、入口、记录、关于。监听 WorkBuddy 和自动写入 Obsidian 已有基础实现，但界面仍保留多目标转发及其文案。

| 当前能力 | 精简桌面端决策 |
| --- | --- |
| 多 Agent、自定义应用、剪贴板、普通文件夹出口 | 从精简桌面端可达界面和命令路由移除 |
| 入口管理、目标选择器、重新发送到其他应用 | 移除，不保留单选 Obsidian 的空壳选择器 |
| 场景、提示词、技能中心 | 从桌面主流程移除 |
| 分批收集、批量分发、粘贴文字导入 | 本期不提供界面入口 |
| 历史记录 | 改为主窗口的最近归档列表 |
| 通用设置、关于 | 合并为一个设置弹窗 |
| WorkBuddy 目录监听、本地暂存、Obsidian 写入 | 复用并补齐可靠性，见配套文档 |
| Windows Share Target 注册与检测 | 不再作为本模式首次使用或完成配置的前提 |

这里的“移除”同时覆盖主窗口、托盘、快捷操作、旧弹窗和自动路由。只隐藏侧边栏、仍让旧 intent 自动发给 Agent，不符合本设计。共享代码可先保留，精简模式不得调用多出口投递。安装形态和旧版升级需要的 Share Target 兼容性单独验证，不直接删除跨平台代码或系统注册。

## 3. 信息架构与窗口规格

界面只有主窗口和设置弹窗；操作系统文件夹选择器继续使用原生控件。首次使用是主窗口的一种状态，不再出现四步、多目标设置向导。

主窗口初始尺寸为 720 × 560 DIP，最小 600 × 460 DIP，可缩放。主体边距 24 DIP，区域间距 20 DIP，控件最小操作高度 32 DIP。窗口标题沿用当前发行版本的应用名；最新主线为“律档通”，旧版为“微信流”，本次不做品牌改名。

沿用 `Themes/AppTheme.xaml` 的绿、白、灰及现有字体。绿色只表示可运行或成功；警告和错误同时使用文字及图标，不依赖颜色。普通文字保持可读对比度，不直接用亮绿色作小字号正文。

不增加侧边栏、顶部标签栏、品牌横幅、累计数字卡片或大面积装饰图。窗口从上到下依次为标题操作区、运行状态、保存位置、最近归档。

### 3.1 标题操作区

- 左侧：当前发行版本的应用名。
- 右侧：一个“设置”按钮；系统标题栏负责最小化和关闭。
- 不放“开始导出”按钮。正常触发动作发生在微信，接收和保存自动完成。

### 3.2 运行状态区

显示一行主要状态和一行必要说明。正常状态提供“暂停接收”；暂停后原位置变为“继续接收”。配置或运行异常时，在该区提供唯一优先修复动作。

| 条件 | 主文案 | 辅助说明 / 动作 |
| --- | --- | --- |
| 未配置知识库 | 选择聊天记录的保存位置 | “选择知识库” |
| 来源目录尚未出现 | 等待 WorkBuddy 导出聊天记录 | “在微信中选择记录并转发到 WorkBuddy。”；“重新检测” |
| 目录可读、监听已启动、尚无成功批次 | 等待微信聊天记录 | “接收目录已就绪。”；“暂停接收” |
| 正在处理 | 正在保存聊天记录 | 显示当前聊天名；其余任务只显示“另有 N 条等待” |
| 本次运行就绪且历史已有成功验证 | 正在接收微信聊天 | “最近保存：今天 14:32”；“暂停接收” |
| 用户暂停 | 已暂停接收 | “继续接收后会补收暂停期间的新记录。”；“继续接收” |
| 来源不可读或监听失效 | 无法接收聊天记录 | 简明原因；“重新检测” |
| 知识库不可写 | 无法保存到知识库 | “已接收的记录会保留，修复后继续保存。”；“检查保存位置” |

列表中单条失败不必把整个监听状态变成失败。在状态区说明“有 N 条记录需要处理”，列表保留具体原因与重试动作。状态合成优先级和内部枚举统一使用配套文档，不由不同控件自行判断。

“WorkBuddy 已连接”“微信已连接”不作为产品文案，因为本产品监听本地文件，并未建立这类连接。历史验证时间也不能代替当前目录和监听健康检查。

### 3.3 保存位置区

显示“保存到：知识库名称 / 子文件夹”，旁边只有“打开知识库”。完整路径放在可访问说明或悬停提示中，长路径在中间省略，不能把主要动作挤出窗口。

未配置时显示“尚未选择知识库”，动作改为“选择知识库”。更改位置统一进入设置，不再弹出目标选择器。

“打开知识库”优先使用可用的 Obsidian 协议；协议未注册或打开失败时回退到资源管理器。Obsidian 未运行不影响写入。

### 3.4 最近归档区

标题为“最近归档”。同一列表内滚动或增量加载，不增加历史管理页。首屏最多呈现约 6 条，按接收时间倒序，状态更新不改变该排序。

| 字段 | 规则 |
| --- | --- |
| 聊天名称 | 优先使用解析或已识别的名称；失败时使用归档文件名，禁止猜测群名 |
| 时间 | 显示接收时间；当天显示时分，跨日显示月日和时分；完整时间可查看 |
| 结果 | 等待保存、正在保存、已保存、部分完成、保存失败、等待源文件等明确文字 |
| 行操作 | 已保存：“打开笔记”；失败：“重试”；等待来源：“重新检查” |
| 次级说明 | 失败原因或部分完成原因，放在该行第二行，允许换行 |

“打开笔记”使用实际写入结果返回的路径，不按聊天名重新拼接。笔记已被外部移动或删除时提示“笔记位置已改变”，提供打开原保存文件夹，不自动生成另一份笔记。

重复 ZIP 由底层去重，不制造重复成功行或重复通知；聊天名称相同但内容有变化的归档仍是独立接收批次，可合并到同一会话笔记。

列表只展示归档结果，不提供“发给…”、“选择场景”、“批量发送”或其他出口。首期不加搜索、筛选器、批量清空或导出历史按钮。

## 4. 首次使用

1. 主窗口直接显示“选择聊天记录的保存位置”和“选择知识库”。后台同时执行来源目录检测。
2. 用户选择已有 Obsidian 知识库；如便携版提供了有效的内置知识库，预填该位置，但仍检查可写性。
3. 校验目标目录可访问，并通过受控临时文件检查写入能力，立即清理探针文件。目标目录不存在时按用户填写的路径新建，并初始化为 Obsidian 知识库（写入 `.obsidian`）。
4. 默认子文件夹为“微信聊天”；已有配置保留原值，如 `31.微信会话`。子文件夹可以在首次真实写入时创建。
5. 保存配置后自动进入接收状态。来源暂未出现时允许完成知识库配置，保留对应等待提示，不把用户困在向导。
6. 显示一句引导：“在微信中选择聊天记录，合并转发到 WorkBuddy，即可自动保存。”首次完整归档成功后移除该引导。

不能通过复制测试 ZIP、创建假目录、启动 WorkBuddy 或发送聊天来假装验证完成。用户进行一次真实转发后，才记录首次端到端成功时间。

知识库目录中存在 `.obsidian` 可作为识别依据；没有该标记时在当前选择区域说明“未识别为现有 Obsidian 知识库”，允许用户明确使用该文件夹，不额外开启强制新建向导。

## 5. 设置弹窗

初始宽度约 520 DIP，跟随主窗口居中。内容可滚动，底部“取消 / 保存”固定。编辑值在保存前不影响运行；验证失败时在字段下说明原因，保留输入。

### 5.1 默认可见项

| 设置 | 默认值 | 行为 |
| --- | --- | --- |
| Obsidian 知识库 | 首次未配置；便携版可预填 | 原生文件夹选择器，只配置一个目标 |
| 保存文件夹 | 新用户“微信聊天” | 仅允许知识库内的相对路径，不接受绝对路径或 `..` 越界 |

“开机启动”与“归档完成通知”不在本弹窗出现：两者都属于使用偏好，由通用设置页承载，同一件事不在两个地方各设一次。

弹窗底部显示版本，以及当前发行形态需要的账号 / 授权入口和现有更新入口；保持低视觉权重。没有已实现的更新能力时不绘制无效“检查更新”按钮。

### 5.2 异常时显示的来源设置

只有自动检测异常（无权限或无法监听）时，才显示当前路径和“重新检测 / 手动指定目录 / 恢复自动检测”。来源路径是 WorkBuddy 的实现细节，正常使用时不需要理解它，所以默认不显示；只有出现需要用户动手修的问题时它才出现。正常使用无需理解 WorkBuddy 内部目录。

不设置“自动导入”和“自动归档”两个并列开关：本产品接收后必然归档；日常控制统一使用“暂停接收”。手动路径仅改变输入来源，不构成第二个输出目标。

### 5.3 保存位置切换

切换前校验新位置，当前正在写入的批次按原目标完成。已有任务持有接收时的目标快照，不能因设置变化悄悄改投新知识库。

待处理任务的旧目标失效时，记录行允许用户明确将该条改用当前保存位置；这是同一归档流程的恢复操作。历史笔记、附件不自动搬迁，也不因切换目录自动重导全部历史。

## 6. 暂停、后台与退出

- 关闭主窗口：隐藏到托盘，继续接收；首次关闭时只提示一次“已在后台接收聊天记录”。
- 托盘双击或默认操作：打开主窗口；右键菜单仅有“打开窗口、暂停接收 / 继续接收、退出”。
- 暂停：立即停止获取新任务；当前已开始写入的任务完成一次事务，队列中其余任务停止。暂停状态持久化，重启仍保持暂停。
- 继续：重新检查来源和目标，重建监听，扫描运行期内未处理的新文件，再继续队列。
- 退出：停止发现新任务，等待当前原子写入阶段收尾并持久化状态，取消其余工作；下次启动恢复。不可把取消标记为成功。

暂停与退出的补收只覆盖源文件仍存在、且符合接收起点规则的记录。WorkBuddy 已清理且本产品尚未暂存的文件无法凭空恢复，见配套文档。

## 7. 失败、通知与数据保留

失败必须先形成持久化记录，再更新界面。短暂 Toast 只能辅助提示，不能代替记录行。接收成功不等于保存成功；笔记和必需附件未完整写入时不能显示“已保存”。

成功通知采用轻提示，不自动弹出 Obsidian，不跳页，不抢焦点。短时间连续完成只合并成一条通知，例如“3 条聊天记录已保存”；前台状态与列表仍逐条更新。关闭成功通知后，主窗口照常显示结果。

部分完成示例：“原始记录已保存，聊天文字未能解析”“笔记已保存，部分图片未提取”。显示“部分完成”，允许针对该批次重试；不冒充完整成功。

成功任务的本地暂存内容在目标完整性核验通过后保留 30 天再清理；未完成、失败、部分完成任务及其已暂存原包不按成功保留期清理。成功去重凭据不随暂存或列表清理删除。知识库中的笔记、附件和 WorkBuddy 原文件始终不由此清理逻辑删除。

该规则覆盖精简模式下旧的 `HistoryRetentionDays` 自动清理语义，不能直接复用会删除失败批次的泛用清理逻辑。磁盘不足时停止继续复制并显示原因，不能通过删除失败记录腾空间。

归档文件布局继续保留最新主线已有的附件分类和“原始归档”目录；界面精简不重排知识库里的旧目录，也不取消分类存储。

## 8. 状态与配置迁移

配置升级版本递增并保留迁移备份。保留现有知识库路径、子文件夹、自启、语言和授权状态。新用户使用新默认值，升级用户不被自动改为“微信聊天”文件夹。

- 原 `WorkBuddyAutoImport` 关闭时迁移为 `ReceptionPaused = true`。
- 原自动归档关闭或缺少知识库时，保持暂停 / 待配置，说明启用后只保存到知识库，不悄悄改变既有操作习惯。
- 精简模式不再使用多出口、场景和收集设置；旧值可保留在备份中，不继续驱动命令。
- `settings.json` 中的知识库配置作为主程序运行配置；`obsidian.json` 是兼容投影，不形成第二份可独立修改的真相。
- 已有历史保留可读；此前发给其他应用的记录标为旧版历史，不能转换成“已保存到 Obsidian”，也不自动重放。

两份配置文件的同步和中断恢复规则见配套文档。迁移不得修改旧笔记正文或原始 ZIP。

## 9. 实现落点与交付顺序

| 位置 | 改造内容 |
| --- | --- |
| `MainWindow.xaml` / `.xaml.cs` | 用单页归档窗口替代侧边栏，不再实例化旧出口面板 |
| 新 `SettingsWindow` | 承载知识库、偏好及异常来源修复 |
| `MainViewModel.cs` / `.LocalImport.cs` | 展示统一运行状态与批次结果，解除 UI 导入锁和后台可靠队列的混用 |
| `Services/WorkBuddyArchiveWatcher.cs`、`App.xaml.cs` | 对接检测、重连和持久化接收服务 |
| `TrayIconService.cs` | 收敛托盘命令，关闭窗口继续运行 |
| `AppSettings.cs` | 配置升级、暂停持久化、通知设置、接收目录覆盖值 |
| `Onboarding/*` | 本模式不进入多目标向导，改用主窗口首次状态 |
| Core 的 `Obsidian/*` 与 Inbox | 补齐结果、目标路径、部分完成和恢复契约 |

实施顺序：先完成配套文档的接收状态与可靠队列，再替换主窗口和设置，最后迁移旧入口与清理命令路由。每一步都保持已有归档数据可读。

## 10. 验收标准

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| UI-01 | 首次启动 | 只有主窗口的知识库配置，没有目标应用选择或侧边栏 |
| UI-02 | WorkBuddy 目录缺失 | 可完成知识库设置，显示等待 / 修复状态，不显示已连接 |
| UI-03 | 正常转发 | 无需桌面端再次点击，记录自动进入列表并保存到唯一目标 |
| UI-04 | 成功归档 | 打开笔记定位到实际文件；未启动 Obsidian 也能保存 |
| UI-05 | 失败与部分完成 | 状态和原因重启后仍可见，可重试且不会显示虚假成功 |
| UI-06 | 关闭窗口 | 托盘继续运行，菜单只有三个操作，无多出口入口 |
| UI-07 | 暂停后恢复 | 状态跨重启保留；恢复时补收符合范围且仍存在的文件 |
| UI-08 | 修改目标 | 当前写入不被中途改投，历史不搬迁、不自动重导 |
| UI-09 | 旧版升级 | 目录和授权等设置保留，旧 Agent 历史不标为知识库成功 |
| UI-10 | 100% / 125% / 150% / 200% DPI | 最小窗口下主要动作可达，长名称和路径不遮挡 |
| UI-11 | 键盘与读屏 | Tab 顺序符合视觉顺序，按钮有名称，状态不只靠颜色表达 |
| UI-12 | 命令路由 | 主窗口、托盘、旧 intent 均不能触发多出口、场景或技能流程 |

上述为后续实现的验收要求，本次文档提交未执行界面或端到端验收。
